## 二、查询方法（先数据库定位、后 MCP 验证）

**第一阶段（数据库检索定位）**
1. `list_domains` / `describe_domain`：确认三个快照均登记于同一知识空间、schema 一致。
2. `query Repository`：确认快照3 仓库构成为快照1、快照2 之和，据此判定"A 点 = 快照1 仓库节点、B 点 = 快照2 仓库节点"。
3. `query/count ApiEndpoint`（按 `repoId=repo:aos-materialized` 过滤）：从数据库取出快照2 侧全部 60 个端点，逐一作为候选拆桥点；`count Function where calledApiIds exists`：取出快照2 侧 59 个发起 API 调用的函数（B 侧终点）。
4. 数据库检索排除了其他跨源关系：快照2 无 Class/Method/Table/Mapper；`count Function where calledApiIds contains "api:asdm-admin-code"` = 0（portal 函数未直连 admin 命名空间端点）。唯一可能的桥接关系为 `apiToBackend`。

**第二阶段（MCP 图查询验证）**
5. `expand`（关系 `apiToBackend`，双向）实测确认：快照2 端点在快照3 中确实存在指向快照1 方法的跨源边（例如 `api:POST:/api/auth/login → AuthController.login`）。
6. `link`（单跳 `apiToBackend`，out 方向）对 60 个快照2 端点**逐个穷举验证**（批查询 50 节点会触发 `BUDGET_EXCEEDED`，故改用 link 逐点查询，60/60 全覆盖）。
7. `trace`（entry=portal 函数，direction=down）端到端验证完整调用链贯通；`aos_expand_snapshot` 用快照专用接口复核桥接边与 `calledBy` 反向边，两种工具结果一致。

## 三、核心结论

**融合快照3 中，快照1 与快照2 之间通过 `apiToBackend`（关联后端方法）关系桥接，共 57 条跨快照通路，全部验证通过。**

通路的统一形态（从 B 侧到 A 侧）：

```
Function（快照2·B点）  --calls 调用-->  ApiEndpoint（快照2·桥接点）  --apiToBackend 关联后端方法-->  Method（快照1·A点）
```

反向阅读即为"从 A 点到 B 点"的通路（A 点出发使用镜像关系）：

```
Method（快照1·A点）  --backendToApi 被前端API调用-->  ApiEndpoint（快照2）  --calledBy 被调用-->  Function（快照2·B点）
```

- **A 点（快照1 侧）**：18 个后端 Controller 类中的 57 个接口方法，分布在 5 个后端模块（core / portal-backend / telemetry / agentorbit / settings）。
- **桥接点（快照2 侧）**：57 个门户 API 端点（快照2 共 60 个端点，57 个成功匹配到后端）。
- **B 点（快照2 侧）**：59 个门户前端 API 函数（分布在 8 个前端服务模块，其中 3 个函数调用的端点无后端匹配，见第五节）。
- 另实测：A 点方法在快照1 内部继续 `calls` 下游 Service/Repository 方法（如 `AuthController.login → UserService.findByEmail / JwtTokenService.generateToken`），通路可在 A 侧继续向深延伸；本报告 A 点取跨源边直接命中的 Controller 方法。

```
          ├─calls→ UserService.validatePassword         [快照1]

```

**aos_expand_snapshot 复核**（节点 `api:POST:/api/auth/login`、`api:GET:/_ai/portal/browse`，关系 `apiToBackend`+`calledBy`，双向）：
- `api:POST:/api/auth/login —apiToBackend→ AuthController.login` ✅（跨源边）
- `api:POST:/api/auth/login —calledBy→ fn:auth.ts:loginWithPassword` ✅
- `api:GET:/_ai/portal/browse —apiToBackend→ PortalController.browseResources` ✅（跨源边）
- `api:GET:/_ai/portal/browse —calledBy→ fn:portalApi.ts:fetchBrowseResources` ✅

与 `link` 查询结果完全一致，桥接边真实存在。

## 七、数据质量观察

1. **桥接边未回写属性**：快照2 端点的 `backendMethodId` 与 `matchedVia` 属性均为空串，但图中存在真实的 `apiToBackend` 边——即融合引擎生成了派生边却未回写节点属性。仅靠 `query` 属性过滤无法发现桥接，必须用 `link`/`expand` 查边（本次查询因此采用"属性定位候选 + 边查询验证"两段式）。
2. **同路径端点未去重**：同一接口在两个源快照中各存一个节点（如 `api:POST:/api/auth/login` 与 `api:asdm-admin-code/POST:/api/auth/login`），融合采用"保留双节点 + 建桥接边"策略，而非节点合并。
3. **参数占位符规范化**：路径参数在两侧命名不同（portal 侧 `{param}`，后端侧 `{guid}`/`{workspaceId}` 等），融合匹配做了参数归一化，按段数与段模式对齐。
4. **查询预算限制**：`expand` 一次传入 50 个节点会触发 `BUDGET_EXCEEDED`（仅返回节点不返回边），批量核验需改用 `link` 单跳查询或 ≤10 节点的小批量 `expand`。
