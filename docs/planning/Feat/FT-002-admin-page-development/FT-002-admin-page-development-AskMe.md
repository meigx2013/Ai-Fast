## 背景摘要

### 核心价值

AI Fast 管理后台（ai-fast-web-admin）是平台运营管理的核心工具，负责内容审核、用户管理、数据监控和系统配置等功能。当前项目仅完成了脚手架搭建（路由、Store、Mock数据），8个视图组件全部缺失，后台无法运行。本特性旨在实现所有视图组件，使管理后台可用。

## 决策点

### 决策点 1：UI 设计风格与布局方案

**问题**：管理后台应采用什么整体设计风格？

**背景**：
- 当前项目已集成 Element Plus，标准后台管理风格是最常见的选型
- 用户端（ai-fast-web-user）已采用现代化设计（渐变色、圆角、动效），后台是否需要保持一致的视觉语言？
- Element Plus 提供了完整的后台管理组件（el-menu、el-table、el-form等），标准方案开发效率最高

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **经典后台风格** — 左侧固定侧边栏 + 顶部面包屑/操作栏 + 内容区，白底配色，标准 Element Plus 主题 | 开发速度快，符合运营人员操作习惯，组件复用度高，维护成本低 | 视觉较传统，与用户端风格割裂 |
| B | **现代管理风格** — 在经典布局基础上加入品牌色渐变、卡片阴影、圆角设计，与用户端视觉语言保持一致 | 品牌一致性更好，视觉更精致 | 开发工作量增加约30%，需自定义更多样式 |
| C | **极简管理风格** — 去除装饰性元素，强调数据密度和操作效率，类似 Notion/Linear 的后台 | 信息密度高，操作效率高 | 需要较多自定义样式，Element Plus 默认样式需大量覆盖 |

**推荐**：✅ 选项 B — 现代管理风格

**确认理由**：
1. 与用户端（FT-001 UI优化）保持品牌一致性，运营管理时不会感觉"换了个产品"
2. Element Plus 的 CSS 变量覆盖机制成熟，自定义成本可控
3. 现代管理风格已成为主流趋势，兼顾美观与效率

**状态**：✅ 已确认

**问题**：Layout 的侧边栏采用固定模式还是可折叠模式？

**背景**：
- 路由已定义6个菜单项（数据统计、内容管理、内容编辑、内容审核、用户管理、系统配置），其中内容编辑为 hidden
- 后台管理系统通常需要在信息密度和操作空间之间权衡

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **固定侧边栏** — 侧边栏始终展开，宽度 220px，显示图标+文字 | 导航始终可见，操作直观 | 内容区宽度受限 |
| B | **可折叠侧边栏** — 默认展开，可通过按钮折叠为 64px 图标模式 | 兼顾导航与空间，灵活性好 | 折叠状态下新用户可能不熟悉图标含义 |
| C | **响应式侧边栏** — 桌面端固定展开，平板端自动折叠，移动端抽屉模式 | 全设备适配 | 开发复杂度最高 |

**推荐**：✅ 选项 B — 可折叠侧边栏

**确认理由**：
1. Element Plus 的 el-menu 原生支持折叠模式，实现成本低
2. 后台管理场景经常需要最大化内容区空间（查看表格、图表）
3. 折叠状态保留图标导航，老用户无障碍

**状态**：✅ 已确认

### 决策点 3：Dashboard 图表方案

**问题**：数据统计仪表盘应展示哪些图表和指标？

**背景**：
- ECharts 已安装（v5.5.0）但未使用
- Mock 数据提供：总用户/总工作流/总浏览/总点赞、今日新增、7天趋势数据、分类分布数据
- Dashboard 是管理员进入后台的第一个页面，需要快速传达平台运营状况

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **核心指标+趋势图+分布图** — 顶部4个统计卡片（总用户/总工作流/总浏览/总点赞），中部7天趋势折线图（用户+工作流+浏览三线），底部分类分布饼图 | 信息完整，一目了然 | 页面较长，数据量少时饼图可能不够直观 |
| B | **精简看板** — 4个统计卡片 + 1个趋势折线图，分类分布用横向柱状图展示 | 紧凑高效，适合小屏幕 | 信息量稍少 |
| C | **丰富仪表盘** — 统计卡片+趋势图+饼图+待审核提醒+最近活动列表+快捷操作入口 | 功能全面，运营信息集中 | 开发工作量大，首屏信息过载 |

**推荐**：✅ 选项 A — 核心指标+趋势图+分布图

**确认理由**：
1. 数据统计页面的核心职责是"一眼看全局"，三项内容覆盖全面
2. Mock 数据已提供完整的 weeklyData 和 categoryDistribution，可直接使用
3. 折线图和饼图是 ECharts 最成熟的基础图表，开发风险低

**状态**：✅ 已确认

### 决策点 4：内容编辑器选型

**问题**：ContentEdit 页面使用什么编辑器方案？

**背景**：
- 工作流内容包含：标题、描述、封面、分类、标签、难度、时长等字段
- 当前 Workflow 数据模型中 description 为纯文本，但实际内容创作可能需要富文本
- 需权衡功能丰富度与开发成本

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **Element Plus 表单** — 纯表单，使用 el-input/el-select/el-tag 等组件，描述用 el-input textarea | 开发最快，无额外依赖，与现有技术栈一致 | 不支持富文本，长内容编辑体验差 |
| B | **富文本编辑器** — 集成 wangeditor/quill 等轻量富文本编辑器 | 支持图文混排，内容编辑体验好 | 新增依赖，需处理图片上传、样式兼容等问题 |
| C | **Markdown 编辑器** — 集成 md-editor-v3 等 Markdown 编辑器 | 适合技术内容，渲染效果可控 | 学习成本，非技术运营人员可能不习惯 |

**推荐**：✅ 选项 A — Element Plus 表单

**确认理由**：
1. 当前数据模型（admin.json）中工作流的 description 为纯文本，无需富文本
2. 后台管理的编辑页主要用于录入结构化数据（标题、分类、标签、状态等），非内容创作
3. 避免引入新依赖，保持项目轻量，后续有需求可渐进式升级
4. 当前为 Mock 阶段，表单方案足够验证业务流程

**状态**：✅ 已确认

### 决策点 5：数据持久化策略

**问题**：后台管理的数据操作是否需要持久化到 localStorage？

**背景**：
- 当前所有 Store 操作都是内存态，刷新页面后数据重置为 admin.json 初始状态
- 用户端（user）的 Store 同样是内存态
- 后台管理场景下，管理员可能同时操作多条数据，刷新丢失体验差

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **纯内存态** — 保持现状，刷新重置 | 实现简单，无需额外代码，Mock 阶段可接受 | 刷新丢失数据，体验差 |
| B | **localStorage 持久化** — 关键数据（工作流列表、用户列表、系统配置）写入 localStorage | 刷新不丢失，体验接近真实系统 | 需处理数据同步、过期清理、容量限制等 |
| C | **Pinia 持久化插件** — 使用 pinia-plugin-persistedstate 自动持久化 | 配置简单，自动同步 | 新增依赖，对所有 Store 生效可能过度 |

**推荐**：✅ 选项 B — localStorage 持久化

**确认理由**：
1. 后台管理的核心操作（审核、用户管理、配置修改）需要数据持久化才有意义
2. 手动实现比插件更可控，只持久化需要的 Store 和字段
3. 避免引入新依赖，保持项目依赖精简
4. 后续对接真实 API 时，持久化代码可平滑替换为 API 调用

**状态**：✅ 已确认

### 决策点 6：内容审核交互设计

**问题**：ContentReview 审核页面采用什么交互方式？

**背景**：
- 工作流有4种状态：published（已发布）、pending（待审核）、rejected（已拒绝）、draft（草稿）
- Store 已实现 approveWorkflow 和 rejectWorkflow 方法
- 审核是后台管理的核心高频操作，需要高效且不易出错

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **列表+弹窗审核** — 表格展示待审核列表，点击"审核"弹出对话框查看详情并填写审核意见 | 操作集中，不易误操作 | 弹窗空间有限，长内容查看不便 |
| B | **列表+抽屉审核** — 表格展示，点击"审核"从右侧滑出抽屉面板展示详情和审核操作 | 空间更大，可展示更多详情 | 抽屉可能遮挡列表信息 |
| C | **列表+内联审核** — 表格行内直接展示审核按钮，点击展开行显示详情 | 最紧凑，无需额外空间 | 展开行空间有限，复杂内容展示受限 |

**推荐**：✅ 选项 B — 列表+抽屉审核

**确认理由**：
1. 审核需要查看工作流详情（标题、描述、标签、封面等），抽屉面板空间充足
2. 抽屉保持列表可见，可快速切换审核不同工作流
3. Element Plus 的 el-drawer 组件成熟，实现成本低

**状态**：✅ 已确认

### 决策点 7：移动端适配需求

**问题**：管理后台是否需要移动端适配？

**背景**：
- 用户端（user）已做完整移动端适配（汉堡菜单、单列布局等）
- 管理后台通常在桌面端使用，但部分运营人员可能需要在手机上处理紧急审核

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **仅桌面端** — 固定 1200px+ 最小宽度，不做移动端适配 | 开发速度最快，表格和图表在桌面端体验最佳 | 手机上无法使用 |
| B | **基础响应式** — 侧边栏移动端变抽屉，表格支持横向滚动，图表自适应宽度 | 手机上可基本使用，关键操作不阻塞 | 开发工作量增加约20%，部分操作在手机上仍不便 |
| C | **完整响应式** — 桌面端+移动端完整适配，移动端有独立的简化操作界面 | 全设备可用 | 开发工作量翻倍，维护成本高 |

**推荐**：✅ 选项 B — 基础响应式

**确认理由**：
1. 紧急审核场景（如内容合规审核）需要移动端可用
2. Element Plus 组件本身支持响应式，基础适配成本可控
3. 侧边栏→抽屉模式是 Element Plus 后台的标准适配方案

**状态**：⏳ 待确认

### 决策点 8：API 层预留设计

**问题**：是否需要在本次开发中预留 API 请求层结构？

**背景**：
- Axios 已安装但未使用，所有数据来自本地 JSON
- 后台管理最终需要对接真实后端 API
- 是否在本次 Mock 阶段就建立 API 层结构，影响后续迁移成本

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **暂不预留** — 直接从 Store 调用 Mock 数据，后续对接 API 时再重构 | 当前开发最快 | 后续重构工作量大，需修改所有 Store 方法 |
| B | **预留 API 层** — 建立 api/ 目录和 axios 实例，当前调用 Mock 函数，后续替换为真实请求 | 架构更清晰，迁移成本低 | 当前开发多一层抽象，需编写 Mock 函数 |
| C | **使用 Mock Service** — 建立 API 层 + MSW 等Mock Service 拦截 | 最接近真实开发体验 | 引入额外依赖和配置，当前阶段过度 |

**推荐**：✅ 选项 A — 暂不预留

**确认理由**：
1. 当前阶段核心目标是"让后台可用"，优先实现8个视图组件
2. Store 层的接口设计已经比较规范（CRUD方法齐全），后续重构为 API 调用时修改点明确
3. 避免过度设计，保持当前阶段的开发速度
4. API 层预留可作为独立的后续特性处理

**状态**：✅ 已确认

### 决策点 9：亮/暗色调切换

**问题**：管理后台是否需要支持亮色/暗色主题切换？

**背景**：
- 用户端（ai-fast-web-user）已实现完整的 Light/Dark 双主题系统（通过 CSS 变量驱动，持久化到 localStorage）
- Element Plus 官方提供暗黑模式支持（`element-plus/theme-chalk/dark/css-vars.css`），通过在 `<html>` 添加 `dark` class 即可切换
- ECharts 图表需要根据主题动态切换配色方案
- 后台管理用户长时间面对屏幕，暗色模式可有效减轻视觉疲劳

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **仅亮色模式** — 只提供标准亮色主题 | 开发最快，无需处理主题适配 | 与用户端体验不一致，长时间使用视觉疲劳 |
| B | **亮/暗双主题切换** — 通过 CSS 变量 + Element Plus 暗黑模式实现，Layout 顶栏提供切换按钮 | 与用户端体验一致，用户可按偏好选择，减轻视觉疲劳 | 需处理 ECharts 图表配色、自定义组件暗色适配，工作量增加约15% |
| C | **跟随系统主题** — 自动检测 `prefers-color-scheme` 跟随系统，同时支持手动切换 | 最智能，自动适配用户系统偏好 | 需同时实现 B 的所有功能，额外增加系统主题监听逻辑 |

**推荐**：✅ 选项 C — 跟随系统主题

**确认理由**：
1. 用户端已有成熟的双主题实现方案，后台可复用相同架构（CSS 变量 + localStorage + dark class）
2. Element Plus 原生支持暗黑模式，仅需引入暗色 CSS 变量文件，成本极低
3. 跟随系统主题是当前主流做法（VS Code、Notion 等均采用），用户无需手动设置即可获得舒适体验
4. 同时保留手动切换能力，满足个性化需求
5. ECharts 可通过 `theme` 配置动态切换配色，实现成本可控

**状态**：✅ 已确认
