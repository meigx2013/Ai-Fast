## 背景摘要

### 核心价值

Web Auto Tester 工具集的 `/auto-test-record` 命令当前通过 Playwright Codegen 录制浏览器操作并转换为 YAML DSL 测试用例。该功能存在多个可改进维度：录制产出的选择器质量不稳定、断言推断过于简单（仅 A1 页面可见）、步骤结构缺乏优化、录制后缺乏交互式审查环节等。本特性旨在对录制生成流程进行系统性优化，提升录制用例的**稳定性、可维护性、完整性**，减少用户手动修改录制用例的工作量。

### 变更范围

| 变更模块 | 变更内容 |
|----------|----------|
| auto-test-record Action | 录制流程6步骤的全面优化升级（选择器优化、断言增强、步骤合并、审查环节等） |
| auto-test-dsl-spec | 可能扩展 Step 字段（如 `comment` 步骤注释、`variables` 数据参数化） |
| auto-test-record规范 | 新增录制优化引擎规范文件（selector-optimizer-spec.md、assertion-inference-spec.md 等） |
| 命令参数 | 扩展 `/auto-test-record` 参数（如 `interactive`、`dataParam`、`selectorStrategy` 等） |

## 决策点

### 决策点 0：录制流程架构 — 逐用例录制模式（核心决策）

**问题**：当前录制模式是"单次录制→单用例产出"，用户需要多次执行 `/auto-test-record` 才能录制多个用例。是否改为"逐用例录制"模式——浏览器持续保持，每完成一个用例由用户决定结束还是继续下一个？

**背景**：
- 当前流程：`/auto-test-record url=xxx` → 启动 Codegen → 用户操作 → 关闭浏览器 → 转换产出 1 个 YAML 文件
- 实际场景中，用户经常需要在同一浏览器会话中连续录制多个测试场景（如：登录→搜索→下单，三个用例共享登录状态）
- 每次重新录制需重新启动浏览器并重新执行前置操作（如重新登录），效率极低
- 用户提出的核心理念：**"简化用例录制的流程，每个用例对应一个录制脚本，每个用例录制完成后由用户决定结束录制还是继续录制下一个用例"**

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **保持当前单次录制模式**：每次 `/auto-test-record` 仅产出1个YAML，多用例需多次执行命令 | 无流程变更；每条命令独立简单 | 多用例需重复前置操作；浏览器状态不共享 |
| B | **逐用例录制模式（推荐）**：一次 `/auto-test-record` 启动浏览器后持续保持，用户完成一个用例操作后发送"完成"信号 → AI 转换当前操作序列为 YAML 并保存 → 提问"继续录制下一个用例还是结束？" → 继续：清空操作缓冲区，用户开始新一轮操作 → 结束：关闭浏览器，输出会话摘要 | ① 浏览器状态共享（如登录态），无需重复前置操作 ② 每个用例独立保存，用例边界自然清晰 ③ 用例间"完成/继续"决策点即天然审查环节 ④ 大幅减少多用例场景的总录制时间 | ① 需新增"完成信号"机制（用户如何告知AI当前用例已完成）② 需维护操作缓冲区（区分不同用例的操作序列）③ 浏览器持续运行增加内存占用 |
| C | **逐用例录制 + 会话状态快照**：选项B + 每个用例完成后保存浏览器状态快照（cookies/storage），下一个用例可选择从快照恢复 | ① 用例间状态可精确恢复 ② 单个用例可从特定快照开始独立执行 | 快照机制增加复杂度；存储空间开销 |

**推荐**：✅ 选项 B — 逐用例录制模式

**确认理由**：
1. 用户明确要求"简化流程、每个用例对应一个录制脚本"，选项B精确匹配该需求
2. 浏览器状态共享是最高频痛点（同一会话中多用例场景占 70%+ 的实际使用场景）
3. "完成/继续"决策点替代了原本复杂的交互式审查环节（决策点3），用例间自然形成审查断点
4. 每个用例独立保存意味着即使后续用例录制中断，已保存的用例不会丢失（间接解决了决策点9的部分问题）
5. 选项C的快照机制可作为未来扩展

**关键子问题（需随此决策一并确认）**：

**子问题 0a：完成信号机制**

用户如何告知 AI "当前用例操作已完成，请转换并保存"？

| 方案 | 描述 |
|------|------|
| S1 | **IDE 输入信号**：用户在 IDE 终端输入特定指令（如 `/next` 或 `continue`），AI 监听终端输入作为完成信号 |
| S2 | **浏览器标记信号**：用户在浏览器中访问特定标记URL（如 `http://localhost:mark-done`），Codegen 捕获该导航作为分割标记 |
| S3 | **快捷键信号**：用户在浏览器窗口按特定快捷键（如 Ctrl+Shift+D），触发 Codegen 事件捕获 |

**推荐**：✅ S1 IDE 输入信号 — 最自然、最可控，与当前 AI 驻留 IDE 的交互模式一致

**子问题 0b：用例命名规则**

逐用例录制模式下，每个用例如何命名？

| 方案 | 描述 |
|------|------|
| N1 | **录制前统一命名 + 序号**：首次命名如 `user-login-flow`，后续自动追加序号 `user-login-flow-2`、`user-login-flow-3` |
| N2 | **每个用例完成时用户指定名称**：每完成一个用例，AI 提问"请命名此用例"，用户输入名称后保存 |
| N3 | **自动命名（URL+操作摘要）**：AI 根据当前用例的首个导航URL和核心操作自动生成名称（如 `login-fill-submit`） |

**推荐**：✅ N2 每个用例完成时用户指定名称 — 精确可控，名称反映业务语义

**子问题 0c：操作缓冲区管理**

如何区分"上一个用例的操作"和"下一个用例的操作"？

| 方案 | 描述 |
|------|------|
| B1 | **时间戳分割**：记录用户发送"完成"信号的时间点，之前的操作归属上一个用例，之后的归属下一个 |
| B2 | **Codegen 输出重置**：每个用例完成时，将已转换的 Codegen 输出清空，后续操作从空缓冲区开始 |
| B3 | **浏览器上下文保持 + Codegen 重启**：保持浏览器窗口，但每个用例完成时重启 Codegen 实例（清空录制缓冲区），用户继续在同一个浏览器操作 |

**推荐**：✅ B3 浏览器上下文保持 + Codegen 重启 — 最干净的操作分割，避免操作混淆

**状态**：✅ 已确认 — 选项 B（逐用例录制模式）

**确认记录**：
- **决策0**：✅ B 逐用例录制模式（用户确认 2026-07-20）
- **子问题0a**：✅ S1 IDE输入信号（用户在IDE终端输入 `/next` 作为完成信号）
- **子问题0b**：✅ N2 每用例完成时用户指定名称
- **子问题0c**：✅ B3 浏览器上下文保持 + Codegen重启（最干净的操作分割）

### 决策点 1：选择器智能优化策略

**问题**：录制产出的 CSS 选择器经常包含不稳定元素（nth-child、动态 ID、长组合路径），如何实现选择器智能优化？

**背景**：
- 当前 Codegen 直接产出原始选择器，如 `.auth-form .el-form-item:nth-child(2) input`
- 不稳定选择器是录制用例最主要的维护痛点
- 用户需要手动替换为 `[data-testid]` 等稳定选择器

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **选择器稳定性评分 + 自动降级优化**：对每个选择器评分（高/中/低），自动尝试降级优化（nth-child→找稳定父级、动态ID→找同级属性、长组合→精简路径），产出优化后选择器 + 评分标注 | 自动化程度高，减少用户手动优化量；保留原始选择器作为 fallback | 优化逻辑复杂，部分选择器可能优化后语义改变 |
| B | **选择器稳定性评分 + 用户手动替换模式**：仅评分标注不稳定选择器，不自动优化，在审核提示中明确标记并提供替换建议（建议使用 data-testid 映射） | 实现简单，不改变选择器语义；用户完全控制 | 用户仍需大量手动工作，自动化程度低 |
| C | **混合模式（推荐优化 + 用户确认）**：自动优化低稳定性选择器，但在审核阶段列出所有优化变更，用户逐条确认或拒绝；拒绝的恢复原始选择器 | 平衡自动化与控制力；用户可快速审核而非逐个手动替换 | 审核流程稍长，需交互式环节 |

**推荐**：✅ 选项 C — 混合模式（自动优化 + 用户确认）

**确认理由**：
1. 录制用例的核心痛点是选择器不稳定，纯标注（选项B）无法显著减少手动工作量
2. 自动优化可能改变选择器语义，需用户确认把关（选项A的风险点）
3. 混合模式让用户快速审核变更而非逐个手动查找和替换，效率最优

**状态**：✅ 已确认 — 选项 C（混合模式：自动优化 + 完成断点展示优化摘要）

### 决策点 2：断言智能推断范围

**问题**：当前录制仅自动添加 A1（页面可见）断言，如何扩展断言智能推断的范围和深度？

**背景**：
- 当前仅对导航步骤添加 A1 页面可见断言
- A1 target 通过 URL 路径硬编码推断表（如 `/login` → `.auth-form`），推断准确性有限
- 录制用例缺乏业务级断言，用户需手动补充大量 A2/A3/A4 等断言

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **仅增强 A1 推断准确性**：改进 URL→元素映射表（增加更多路径模式），保持仅添加 A1 断言 | 改动小，兼容现有规范；A1 断言保证基本页面验证 | 断言覆盖面仍然窄，用户需手动补充大量断言 |
| B | **扩展到 4 类断言推断（A1+A2+A4+A6）**：A1 页面可见 + A2 URL跳转（导航后）+ A4 内容匹配（点击后推断关键文本）+ A6 表单值（type操作后验证输入值） | 覆盖最常见验证场景；大幅减少用户手动补充断言量 | 推断逻辑复杂，部分推断可能不准确（需标注置信度） |
| C | **全量断言推断引擎（A1~A8 按场景推断）**：根据每个操作的上下文推断最适合的断言类型，包括 A3 元素状态、A7 元素数量等 | 最全面覆盖；产出的用例最接近可执行状态 | 推断引擎最复杂；部分断言类型（A5 API拦截、A8 截图比对）录制场景不适合 |

**推荐**：✅ 选项 B — 扩展到 4 类断言推断（A1+A2+A4+A6）

**确认理由**：
1. A1+A2+A4+A6 覆盖录制场景中 80%+ 的常见验证需求
2. A3（元素状态）和 A7（元素数量）推断需更多页面上下文信息，录制时难以可靠获取
3. A5（API拦截）和 A8（截图比对）属于 Playwright 专有高级断言，不适合录制自动推断
4. 推断结果标注置信度（高/中/低），用户可在审查环节调整

**状态**：✅ 已确认 — 选项 B（A1+A2+A4+A6 四类断言推断 + 置信度标注）

### 决策点 3：每用例完成时的优化建议展示（原：录制后交互式审查环节）

**问题**：逐用例录制模式下，每个用例完成时用户会发送 `/next` 信号触发转换保存。在这个"完成/继续"决策断点处，是否展示优化建议（选择器优化、断言推断、步骤合并）？

**⚠️ 受决策点0确认影响，此决策点已重构**：
- 原问题：是否新增独立审查步骤（Step 7）
- 新问题：逐用例模式下"完成/继续"决策点天然形成审查断点，`interactive` 参数的含义从"是否增加独立审查步骤"变为"每用例完成时是否展示优化/断言建议清单"

**背景**：
- 决策点0确认B后，每个用例完成时用户必须做出"继续/结束"决策，此时天然形成交互断点
- 在此断点展示优化建议（选择器变更、断言推断、步骤合并）可让用户快速确认/调整，无需额外审查步骤
- 但优化建议展示会增加每个用例的"完成→保存"间隔时间

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **不展示优化建议，直接保存**：每用例完成时仅提问"命名+继续/结束"，不做优化展示，用户后续手动查看YAML修改 | 最快流程；每用例保存间隔极短 | 用户仍需手动逐文件检查和修改选择器、断言等 |
| B | **每用例完成时展示优化摘要（推荐）**：在 `/next` 信号后展示：① 选择器优化变更摘要（N条已优化，列出关键变更）② 断言推断摘要（添加了X条A1/A2/A4/A6断言）③ 步骤合并摘要（合并了X组连续操作）④ 用户快速确认后保存 YAML | 用户在每个用例保存前可快速审视优化内容；无需打开YAML手动修改 | 每用例完成时增加短暂等待（展示+确认） |
| C | **可选展示（参数控制）**：新增 `interactive=true/false` 参数，默认 true 展示优化摘要；设 false 时直接保存不展示 | 兼顾快速场景和精细场景；灵活 | 参数增加复杂度 |

**推荐**：✅ 选项 B — 每用例完成时展示优化摘要

**确认理由**：
1. 决策点0确认后，"完成/继续"断点是唯一自然交互点，在此展示优化建议无需额外步骤
2. 优化摘要而非逐条确认（简化版审查），用户仅需快速浏览确认，不影响流程流畅度
3. 展示内容为"摘要"而非"逐条确认"，避免审查环节过长
4. 如果用户不满意优化结果，可直接修改YAML文件（而非在审查环节逐条拒绝）

**状态**：✅ 已确认 — 选项 B（每用例完成时展示优化摘要）

### 决策点 4：步骤优化与合并策略

**问题**：录制产出的步骤是 Codegen 的 1:1 原始映射，是否需要步骤优化（合并、去冗余、智能等待补充）？

**背景**：
- Codegen 录制的步骤是原始操作序列，可能包含：连续 type 操作可合并为"填写表单"、重复 wait 可精简、导航前的 wait 可能冗余
- 当前仅在 click（提交按钮）后补充一个 wait，覆盖面窄

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **保持 1:1 映射 + 仅增强等待补充**：不合并步骤，仅扩展 wait 补充规则（click后→wait目标元素、navigate后→wait页面核心元素） | YAML DSL Step 结构不变；不引入合并复杂性 | 步骤可能冗余（如连续5个type操作分5步） |
| B | **步骤合并 + 智能等待 + 去冗余**：① 连续 type→合并为表单填写组（可选注释标注）② 冻结/重复 wait→去冗余 ③ 扩展等待补充规则（提交、导航、异步加载场景）④ 将合并建议在审查环节展示 | 产出步骤更精练；执行效率更高 | 合并逻辑需谨慎处理（合并后步骤语义需保持清晰） |
| C | **步骤合并为可选策略**：新增 `optimizeSteps=true/false` 参数控制是否启用步骤合并优化，默认 true；合并仅合并连续同类型操作（type序列），不跨类型合并 | 用户可选择精练或原始步骤；合并范围可控 | 合并语义仍需定义清晰规则 |

**推荐**：✅ 选项 B — 步骤合并 + 智能等待 + 去冗余

**确认理由**：
1. 录制用例的步骤冗余是常见痛点，1:1 映射产出的步骤数远多于手动编写
2. 连续 type 操作合并为表单填写组是自然语义，不破坏步骤可读性
3. 智能等待补充覆盖更多场景，提升用例执行稳定性
4. 合并建议在审查环节展示，用户可拒绝不合意的合并

**状态**：✅ 已确认 — 选项 B（步骤合并 + 智能等待 + 去冗余）

### 决策点 5：数据参数化支持

**问题**：录制产出的用例中输入值（用户名、密码等）是硬编码的，是否支持数据参数化提取？

**背景**：
- Codegen 录制的 `page.fill('selector', 'testuser')` → `value: testuser` 是硬编码
- 硬编码数据导致用例无法复用不同测试数据
- 当前 DSL spec 无 variables/parameters 字段

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **不参数化，保持硬编码**：录制产出直接使用录制时的输入值，用户需手动提取参数 | 无 DSL spec 变更；实现简单 | 用例可复用性差；多数据集测试需手动改 YAML |
| B | **自动参数化提取**：自动识别 type 操作的 value，提取为 `metadata.parameters` 字段，步骤中引用 `{{paramName}}`；在审查环节展示参数化建议供确认 | 用例可直接复用不同数据集；符合测试最佳实践 | 需扩展 DSL spec 增加 parameters 字段；参数化推断可能不准确（如搜索关键词 vs 固定选项） |
| C | **可选参数化（参数控制）**：新增 `dataParam=true/false` 参数，默认 false 不参数化；设 true 时自动提取并在审查环节确认 | 兼顾简单场景和参数化需求；灵活 | 默认不参数化可能让多数用户错过此功能 |

**推荐**：✅ 选项 C — 可选参数化（参数控制，默认 false）

**确认理由**：
1. 数据参数化需要扩展 DSL spec，影响范围较大，默认关闭降低风险
2. 需要参数化的场景（如多数据集回归测试）是高级需求，用户可按需开启
3. 参数化提取在审查环节确认，避免自动推断错误
4. `dataParam=true` 时审查环节自动展示参数化建议表

**状态**：✅ 已确认 — 选项 C（可选参数化，dataParam 参数，默认 false）

### 决策点 6：A1 断言推断方式改进

**问题**：当前 A1 断言的 target 通过硬编码的 URL→元素映射表推断（如 `/login` → `.auth-form`），准确性有限。如何改进？

**背景**：
- 硬编码映射表仅覆盖常见路径（login/home/admin/products 等）
- 未知路径 fallback 到 `.page-content` 或 `body`，几乎无验证价值
- 无法适配不同项目的前端组件结构

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **扩展硬编码映射表**：增加更多路径模式（如 `/register`→`.register-form`、`/settings`→`.settings-panel` 等） | 简单直接；无需额外信息 | 仍是硬编码，无法适配自定义项目 |
| B | **页面结构动态推断**：录制结束后通过 Playwright 获取页面 DOM 结构，自动推断核心可见元素（优先级：[data-testid] > h1/h2标题 > .main/.content > body）；推断结果标注置信度 | 适配任何项目；推断基于实际页面结构 | 需额外 DOM 分析步骤；推断可能不准确 |
| C | **用户提供页面元素映射文件**：用户在录制前提供 `page-element-map.yaml`（定义各 URL 路径的核心元素选择器），录制时自动引用 | 最准确；用户完全控制 | 需用户预先准备映射文件；首次录制无映射可用 |

**推荐**：✅ 选项 B — 页面结构动态推断（优先使用 C 的映射文件作为补充）

**确认理由**：
1. 动态推断适配任何项目，无需用户预先准备
2. 推断优先级规则（data-testid > 标题元素 > 主内容区）覆盖大多数页面结构
3. 推断置信度标注让用户在审查环节可调整不准确推断
4. 同时支持选项C的映射文件作为可选补充（`pageMapFile` 参数），提供最高准确性

**状态**：✅ 已确认 — 选项 B（页面结构动态推断 + 可选映射文件）

### 决策点 7：录制元数据增强

**问题**：当前录制仅记录基础 metadata（targetUrl、timeout、browser），是否增强录制上下文信息？

**背景**：
- 缺少录制时间戳、录制持续时间、页面标题等信息
- 缺少前端框架信息（Vue/React/Angular）影响选择器策略
- 缺少页面关键结构信息（如是否有 data-testid 属性）

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **保持当前 metadata 不变**：仅记录 targetUrl、timeout、browser | 无 spec 变更；简单 | 丢失重要上下文信息，影响后续优化 |
| B | **增强 metadata（推荐）**：新增 `recordedAt`（录制时间）、`duration`（录制耗时）、`pageTitle`（页面标题）、`pageStructure`（关键结构标记：hasDataTestId/frontFramework）、`viewportActual`（实际视口尺寸） | 为断言推断、选择器优化提供上下文；为报告和追踪提供信息 | 需扩展 metadata 子字段定义 |
| C | **增强 metadata + 录制摘要日志**：选项B的 metadata 增强 + 生成 `recording-summary.json`（完整录制上下文：操作统计、页面快照摘要、选择器分析报告） | 最完整的上下文；可独立用于分析和优化 | 额外文件产出；信息量大可能冗余 |

**推荐**：✅ 选项 B — 增强 metadata

**确认理由**：
1. 关键上下文信息（pageStructure.hasDataTestId、frontFramework）直接影响选择器优化策略
2. recordedAt 和 duration 是基础追踪信息，对报告和历史对比有价值
3. 选项C的 recording-summary.json 可作为未来扩展，当前 metadata 增强已足够

**状态**：✅ 已确认 — 选项 B（增强 metadata）

### 决策点 8：多页面/iframe/弹窗支持

**问题**：当前录制仅捕获单页面线性操作序列，是否扩展到多页面/iframe/弹窗场景？

**背景**：
- Codegen 可录制 tab 切换和 popup 操作，但当前解析规则未处理
- iframe 内操作在 Codegen 中可能以不同上下文产出
- 弹窗（dialog/modal）操作是常见场景

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **不扩展，保持单页面线性录制**：忽略 tab/popup/iframe 操作，仅保留主页面操作序列 | 实现简单；不引入 DSL 新概念 | 无法录制多页面交互场景（如：点击链接→新tab→操作→回到原tab） |
| B | **支持多页面/弹窗（不含 iframe）**：扩展 Codegen 解析规则处理 `page.waitForEvent('popup')`、多 context 操作；YAML DSL 新增 `pageContext: main/popup/newTab` 字段 | 覆盖 popup 和 tab 切换场景（常见需求） | 需扩展 DSL Step 字段；iframe 仍不支持 |
| C | **全面支持多页面/iframe/弹窗**：选项B + iframe 操作通过 `frameLocator` 解析，新增 `iframe: selector` 字段 | 最全面覆盖；录制可用性最高 | iframe 解析最复杂；DSL 变动最大 |

**推荐**：✅ 选项 B — 支持多页面/弹窗（不含 iframe）

**确认理由**：
1. popup/dialog 和 tab 切换是 Web 测试常见场景，不支持会导致大量录制失败
2. iframe 场景相对少见且解析复杂度高，可在后续版本扩展
3. `pageContext` 字段变更小且语义清晰
4. iframe 支持作为 🔵 规划中项目记录

**状态**：✅ 已确认 — 选项 B（支持多页面/弹窗，不含iframe）

### 决策点 9：录制中断恢复机制

**问题**：录制过程中如浏览器意外关闭或 Codegen 崩溃，当前无恢复机制。是否新增中断恢复？

**背景**：
- Codegen 录制是交互式过程，浏览器意外关闭会丢失所有录制数据
- 长时间录制（如多页面流程）中断后重新录制成本高
- Codegen 本身无中间保存机制

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **不支持中断恢复**：依赖 Codegen 原生机制，中断后提示用户重新录制 | 无额外实现；简单 | 长录制中断体验差 |
| B | **实时操作缓存**：录制过程中实时缓存已解析的操作序列到临时文件（`.asdm/workspace/auto-test/cases/.recording-cache-{name}.json`），中断后可从缓存恢复并继续 | 长录制不怕中断；可从断点恢复 | 需实时解析 Codegen 输出（Codegen 无实时输出 API，需创新方案） |
| C | **中断恢复为可选功能**：核心录制无恢复机制；在 roadmap 中标记为 🔵 规划中项目，后续版本实现 | 当前实现简单；未来有规划 | 当前版本无恢复能力 |

**推荐**：✅ 选项 C — 中断恢复为可选功能（当前不实现，规划中标记）

**确认理由**：
1. Playwright Codegen 无实时输出流 API，实时缓存实现技术难度高
2. 录制通常是短时间操作（几分钟），中断概率相对低
3. 核心改进方向（选择器优化、断言增强、审查环节）优先级高于中断恢复
4. 标记为规划中项目，后续版本可评估实现

**状态**：✅ 已确认 — 选项 C（当前不实现，标记为规划中项目）

### 决策点 10：与已有用例对比避免重复

**问题**：录制产出的用例可能与已有用例功能重复，是否增加重复检测？

**背景**：
- `.asdm/workspace/auto-test/cases/` 目录可能已有相同场景的手写/AI生成用例
- 录制新用例前无重复检测，可能产出冗余用例

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | **不增加重复检测**：录制直接产出，用户自行判断是否重复 | 简单；无额外逻辑 | 可能产出冗余用例 |
| B | **录制前提示已有相似用例**：录制前扫描 cases/ 目录，基于 URL 和 tags 匹配相似用例，提示用户"已有相似用例 {name}，是否继续录制？" | 避免明显重复；提示信息实用 | 匹配逻辑可能误判（URL相似但场景不同） |
| C | **录制后对比 + 合并建议**：录制完成后与已有用例对比步骤序列相似度，在审查环节提示相似用例并提供合并建议 | 更精确的重复检测；合并建议实用 | 步骤序列对比算法复杂；合并建议需用户判断 |

**推荐**：✅ 选项 B — 录制前提示已有相似用例

**确认理由**：
1. 基于URL+tags的简单匹配可快速避免明显重复
2. 录制前提示比录制后对比更及时（用户可在录制前决定是否继续）
3. 选项C的步骤序列对比算法复杂度高，作为未来扩展

**状态**：✅ 已确认 — 选项 B（录制前提示已有相似用例）
