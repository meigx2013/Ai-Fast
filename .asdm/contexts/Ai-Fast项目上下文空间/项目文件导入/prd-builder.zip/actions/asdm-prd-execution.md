# asdm-prd-execution 操作指令

## 目的

本指令指导 AI 模型执行功能任务。它基于任务计划和 Task PRD 执行任务，并更新任务列表状态。

## 语言检测

在执行任何任务之前，必须检测并使用当前环境的响应语言：

1. **检测响应语言**：分析环境设置以确定主要语言
2. **应用语言一致性**：确保所有交互使用检测到的语言
3. **支持的语言**：英语 (en)、中文 (zh)

**重要提示**：语言检测是第一个步骤。

## 上下文注入

### 核心原则

```
┌─────────────────────────────────────────────────────────────┐
│  L1 索引（必须）→ L2 索引（按需）→ 源码（按需）              │
│                                                             │
│  不一次性加载所有上下文，按任务需要逐步加载                   │
│  源码是权威来源                                             │
└─────────────────────────────────────────────────────────────┘
```

### 加载顺序

| 阶段 | 加载内容 | 必须 |
|------|----------|------|
| 1. 初始 | `.asdm/contexts/index.md` + Task List + Feature PRD | ✅ |
| 2. 任务选择 | 加载选定任务的 Task PRD | ✅ |
| 3. 任务执行 | 根据需要加载 L2 索引和源码 | 按需 |

### 步骤 1: 读取 L1 项目顶层索引（必须）

**必须首先读取**：

1. **`.asdm/contexts/index.md`** - 项目全局结构
   - 目的：了解项目整体结构和技术栈

2. **Task List**
   - 路径：`.asdm/workspace/features/<feature-id>-<feature-name>/task-list.md`
   - 目的：了解可用任务及其状态

3. **Feature PRD**
   - 路径：`.asdm/workspace/features/<feature-id>-<feature-name>/feature-prd.md`
   - 目的：了解功能整体需求

### 步骤 2: 加载选定任务的 Task PRD（必须）

对于要执行的任务：

- **路径**：`.asdm/workspace/features/<feature-id>-<feature-name>/<task-id>-<task-name>-prd.md`
- **目的**：获取任务的详细需求和实现指导
- **如果不存在**：提示用户先使用 `/asdm-prd-breakdown` 生成

### 步骤 3: 根据任务加载 L2 索引（按需）

根据任务涉及的领域，按需读取领域索引：

- **如果任务涉及用户模块**：
  - 读取：`.asdm/contexts/domains/user-domain.md`

- **如果任务涉及数据访问**：
  - 读取相关的领域索引
  - 了解 Entity/Repository 结构

- **如果任务涉及 API 开发**：
  - 读取相关的领域索引
  - 了解 Controller/Service 结构

### 步骤 4: 按需访问源码（按需）

**这是最重要的上下文来源**：

1. **根据 L2 索引的路径**：
   - 读取相关的领域索引文件
   - 根据索引中的"关键文件"路径读取源码

2. **直接读取要修改/参考的源码**：
   - Entity/Model 源码
   - Repository/DAO 源码
   - Service 源码
   - Controller 源码

3. **源码是权威来源**：
   - 上下文索引仅供参考
   - 以源码的实际实现为准
   - 不要基于不完整的上下文做出假设

### 执行阶段上下文使用

```
任务执行流程：

1. 读取 Task PRD → 了解要做什么
2. 读取 L2 索引 → 了解领域结构
3. 读取相关源码 → 了解现有实现
4. 基于实际代码 → 执行实现
5. 验证实现 → 运行编译/测试命令
```

### 错误处理

如果上下文文件不存在：

```markdown
1. 如果 `.asdm/contexts/index.md` 不存在：
   → 直接扫描项目目录了解结构

2. 如果 `.asdm/contexts/domains/<领域>-domain.md` 不存在：
   → 直接扫描该领域的目录
   → 根据实际代码分析

3. 如果找不到需要的上下文：
   → 直接扫描源码目录
   → 基于实际代码执行任务
   → 不要假设，按实际代码操作
```

## 任务执行步骤

### 1. 识别功能并验证存在

识别要执行任务的功能：
- 从用户获取功能 ID 或名称
- 验证功能目录存在
- 验证任务列表存在
- 如果不存在，提示用户先使用 `/asdm-prd-planning`

### 2. 加载功能上下文

加载必要的上下文文件：
- Task List（必须）
- Feature PRD（必须）
- 按需加载 L2 索引和源码

### 3. 展示可用任务

向用户展示可用任务：
- 显示所有任务的任务 ID、名称和状态
- 突出显示可执行的任务（`TODO` 状态，无阻塞依赖）
- 如果用户未指定任务 ID，提示用户选择

### 4. 选择执行的任务

确定要执行的任务：
- 验证任务存在且可执行
- 检查任务依赖是否满足
- 获取用户确认

### 5. 检查 Task PRD 存在性

检查选定任务的 Task PRD：
- 如果存在，加载它
- 如果不存在：
  - 提示用户先使用 `/asdm-prd-breakdown`
  - 等待 Task PRD 生成完成

### 6. 确认任务执行

向用户展示任务详情并获取确认：
- 任务 ID 和名称
- 任务描述
- 验收标准
- 任何依赖或风险

### 7. 更新任务状态为进行中

更新任务列表：
- 状态从 `TODO` 更新为 `IN PROGRESS`

### 8. 执行任务

基于 Task PRD 实现任务：

1. **读取 L2 索引和源码**（按需）
   - 根据任务涉及的领域加载索引
   - 根据索引路径读取相关源码

2. **编写代码**
   - 按照 Task PRD 的实现方法
   - 遵循项目编码规范
   - 实现验收标准

3. **渐进式验证**
   - 编写代码后运行快速验证：
     - 编译检查：`mvn compile`、`npm run build`
     - 语法检查：语言特定的验证器
     - 测试运行：如有测试

4. **如有需要，更新 L3 上下文**
   - 如有生成详细内容，确保与源码一致

### 9. 验证任务完成

**关键**：验证必须通过**执行**验证命令完成：

1. **提取验证步骤**
   - 从 Task PRD 提取验证步骤
   - 提取验收标准中的验证工具

2. **执行验证命令**
   ```bash
   # Java 项目
   mvn clean compile    # 编译检查
   mvn test            # 运行测试
   mvn checkstyle:check # 代码风格

   # JavaScript/TypeScript 项目
   npm run build       # 构建
   npm test           # 测试
   npm run lint       # 代码质量
   ```

3. **验证验收标准**
   - 检查所有验收标准是否满足
   - 确保与 Feature PRD 一致

4. **处理验证失败**
   - **不要**标记为 DONE
   - 分析错误
   - 修复问题
   - 重新验证

### 10. 更新任务状态

更新任务列表：
- 成功：状态更新为 `DONE`
- 失败：状态更新为 `BLOCKED` 或 `TODO`

**检查所有任务是否完成**：
- 如果所有任务标记为 `DONE`：
  - 更新 Feature 状态为 `COMPLETED`
- 如果有任务未完成：继续下一个任务

### 11. 展示执行摘要

展示任务执行摘要：
- 任务 ID 和名称
- 最终状态
- 完成的工作
- 创建/修改的文件
- **验证结果**：执行的命令和结果
- 任何问题或警告
- 建议的后续步骤

## 任务执行最佳实践

### 1. 遵循 Task PRD

- 严格按照 Task PRD 的需求和验收标准
- 不要偏离实现方法，除非获得用户批准
- 如果不明确，询问后再继续

### 2. 源码为准

```
重要原则：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   上下文索引仅供参考                                         │
│   源码是权威来源                                             │
│                                                             │
│   如果上下文与源码不一致：                                   │
│   → 以源码为准                                              │
│   → 不要基于不完整的上下文做出假设                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3. 代码质量

- 遵循项目编码规范
- 编写清晰、可读、可维护的代码
- 执行验证工具确保代码质量

### 4. 验证执行（必须）

**关键要求**：验证必须通过**执行命令**，而非描述要运行什么：

1. 提取验证命令
2. 执行每个验证命令
3. 分析结果
4. 修复问题后再完成

### 5. 状态更新

- 状态变化时立即更新任务列表
- 保持用户知情
- 及时报告任何问题

## 使用方法

AI 模型应：

1. 从用户获取功能信息
2. 检测响应语言
3. 验证功能存在
4. 加载上下文（index.md → Task List → 按需加载 L2/源码）
5. 展示可用任务
6. 选择任务
7. 检查 Task PRD
8. 确认执行
9. 更新状态为 `IN PROGRESS`
10. 执行任务（读取源码 → 编写代码 → 验证）
11. 更新状态为 `DONE` 或 `BLOCKED`
12. 展示执行摘要

## 输出摘要

### 更新的文档

- **任务列表**：更新当前任务状态

### 实现产物

- **源文件**：基于任务需求创建或修改
- **测试文件**：单元测试或集成测试（如需要）

### 执行摘要

```
任务执行摘要
======================
任务 ID: T001
任务名称: 实现用户服务 API
状态: DONE

验证结果:
✓ 编译: mvn compile - PASSED
✓ 测试: mvn test - PASSED (12/12 tests)
✓ 代码风格: mvn checkstyle:check - PASSED
```
