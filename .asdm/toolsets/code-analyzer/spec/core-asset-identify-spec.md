## Overview

本规范定义了核心资产识别报告的结构和格式要求。此类文档用于分析代码中的引用关系，识别被引用次数达到阈值（默认 3 次及以上）的类和方法作为核心代码资产。这些高引用代码通常是项目的核心资产，在进行代码重构或架构调整时需要特别关注。

**主要用途**：

- 识别代码库核心依赖，避免破坏性修改
- 重构前评估影响范围
- 发现潜在的耦合问题和循环依赖
- 确定代码库中需要重点保护的资产

## Section Guidelines

### 元信息 (Metadata)

报告开头应包含以下元信息：

- **分析路径**：被分析的代码库路径
- **引用阈值**：核心资产的最小引用次数（默认 3）
- **分析时间**：报告生成的时间戳
- **语言**：检测到的响应语言

### 执行摘要

用 2-3 句话概括：

- 代码库核心资产的总体情况
- 关键的核心类和方法的数量
- 潜在的架构风险

### 统计概览

统计表格应包含：

- **核心类数量**：引用次数 >= 阈值的类总数
- **核心方法数量**：引用次数 >= 阈值的方法总数
- **总引用次数**：所有核心资产的引用次数总和
- **最高引用次数**：单一资产的最大引用次数
- **平均引用次数**：总引用次数除以资产数量

### 高引用类表格

列出所有高引用类（按引用次数降序）：

**字段说明**：

- **类名**：类的完整名称
- **引用次数**：在代码库中被引用的总次数
- **定义位置**：首次定义的完整文件路径
- **所属模块**：根据路径推断的功能模块名称

**排序规则**：

- 按引用次数降序排列
- 引用次数相同时按类名字母序排列

### 高引用方法表格

列出所有高引用方法（按引用次数降序）：

**字段说明**：

- **方法名**：方法的完整名称
- **引用次数**：在代码库中被调用的总次数
- **定义位置**：首次定义的完整文件路径
- **所属模块**：根据路径推断的功能模块名称

**排序规则**：

- 按引用次数降序排列
- 引用次数相同时按方法名字母序排列

### 依赖关系分析

分析核心资产之间的依赖关系：

**核心依赖概览**：

- 描述核心资产之间的主要依赖方向
- 识别关键依赖节点（被多个模块依赖）

**模块耦合度**：

- 统计每个模块被依赖的次数
- 统计每个模块依赖其他模块的数量
- 识别高耦合模块

**耦合风险**：

- 识别循环依赖（如果有）
- 发现潜在的耦合问题
- 提出优化建议

## Usage Guidelines

生成核心资产识别报告时：

1. **步骤 1**：接收用户提供的分析路径和阈值参数
2. **步骤 2**：验证输入路径有效性
3. **步骤 3**：扫描并识别所有代码文件
4. **步骤 4**：识别类和方法定义
5. **步骤 5**：追踪并统计引用关系
6. **步骤 6**：根据阈值过滤核心资产
7. **步骤 7**：分析依赖关系
8. **步骤 8**：生成 Markdown 格式报告
9. **步骤 9**：保存报告到指定目录

**引用识别模式**：

- **类引用**：`new ClassName()`、`import ClassName`、`ClassName.method()`
- **方法引用**：`functionName()`、`obj.methodName()`、`module.functionName()`

**统计规则**：

- 同一个文件内的引用计入
- 不同文件间的引用计入
- 注释中的引用不计入

## Best Practices

处理核心资产识别时：

1. **全面扫描**：覆盖所有支持的编程语言文件
2. **准确识别**：正确区分定义和引用
3. **合理阈值**：默认使用 3 次，可根据项目规模调整
4. **依赖分析**：识别单向依赖和双向依赖

### Common Pitfalls to Avoid

- **遗漏引用**：未正确识别间接引用（如通过继承）
- **混淆定义和引用**：将类/方法定义误判为引用
- **忽略上下文**：未考虑包名/命名空间的差异
- **报告过于冗长**：核心资产过多时应分页或筛选
