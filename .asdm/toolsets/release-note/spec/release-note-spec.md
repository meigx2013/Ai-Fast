# Release Note 规范模板

## Language Guidelines

此 Release Note 文档必须使用环境中检测到的响应语言。确保文档中的所有内容遵循以下规则：

1. **语言一致性**：整个文档使用同一种语言
2. **写作规范**：遵循所检测语言的写作风格和格式
3. **清晰性**：确保内容清晰易懂

**支持的语言**：

- 中文（zh）
- 英文（en）
- 其他基于环境检测的语言

---

## Overview

本规范定义了 Release Note 文档的结构和格式要求。此类文档用于记录软件版本发版的完整变更内容，包括基本信息、版本概述、新功能、功能优化、Bug 修复、数据与配置变更、依赖变更、上线影响与回滚策略、验证情况等，帮助用户和团队全面了解每个版本的变更详情及上线影响。

**主要用途**：

- 向团队和用户传达版本变更内容
- 记录新功能、缺陷修复和用户故事的实现情况
- 提供数据/配置变更和依赖变更的追踪
- 提供上线影响评估与回滚策略
- 作为发版流程的正式文档输出

---

## Document Structure

使用以下模板结构生成 Release Note 文档：

```markdown

| 项目 | 内容 |
|------|------|

| 版本号 | <版本号> |
| 发布类型 | <常规迭代 / 热修复 / 紧急上线> |
| 发布日期 | <YYYY-MM-DD> |
| 发布窗口 | <HH:MM – HH:MM> |
| 影响范围 | <Web 端 / App / 后台服务 / ...> |
| 扫描分支 | <目标分支名称，默认 release> |
| 起始提交 | <from-ref> |
| 目标提交 | <to-ref> |

## 版本概述

<对本次发布做什么、为什么做的简要说明，2-3 句话概括核心内容>

|------|-----------|--------|------|----------|
| <模块编号+名称> | <Submodule> | <功能点> | <功能说明> | <需求 ID> |

<!-- 如需展示用户故事 DoD，在新功能表格后补充 -->

**关联用户故事 DoD**：

| 用户故事 ID | 标题 | DoD | 状态 |

| 模块 | Submodule | 优化点 | 效果 |

| 模块 | Issue ID | 问题描述 | 影响范围 |
|------|----------|----------|----------|

| Submodule | 变更项 | 说明 |
|-----------|--------|------|

| Submodule | 依赖项 | 变更前版本 | 变更后版本 |
|-----------|--------|-----------|-----------|

- <上线影响说明>
```

**Key Elements**：

- **基本信息（Header）**：系统名称、版本号、发布类型、发布日期、发布窗口、影响范围、扫描分支、起止提交
- **版本概述**：简要说明本次发布做什么、为什么做
- **变更概览**：各 Submodule 的提交数、变更文件数、行数统计
- **分类变更章节**：新功能、功能优化、Bug 修复、数据/配置变更、依赖变更（均含 Submodule 和模块列）
- **上线影响与回滚策略**：上线影响评估及回滚方案
- **验证情况**：测试验证结果
- **备注**：其他需要说明的事项

## Section Guidelines

### 基本信息（Header）Section

基本信息部分应包含：

- **系统名称**：发版系统或产品的名称
- **版本号**：本次发版的版本号
- **发布类型**：常规迭代、热修复或紧急上线
- **发布日期**：计划发布日期
- **发布窗口**：发布的时间窗口
- **影响范围**：受影响的系统或端
- **扫描分支**：代码差异扫描所使用的 Git 分支
- **起始/目标提交**：Git 提交引用

**Important**：

- 所有字段必须填写
- 发布类型只能从"常规迭代"、"热修复"、"紧急上线"中选择

**Example**：

```markdown
| 项目 | 内容 |
|------|------|
| 系统名称 | 订单管理系统 |
| 版本号 | V1.5.0 |
| 发布类型 | 常规迭代 |
| 发布日期 | 2026-06-04 |
| 发布窗口 | 20:00 – 22:00 |
| 影响范围 | Web 端 / App / 后台服务 |
| 扫描分支 | release |
| 起始提交 | v1.4.0 |
| 目标提交 | v1.5.0 |
```

### 版本概述 Section

版本概述部分应包含：

- 本次发版做什么
- 为什么做
- 核心变更的简要概括

**Important**：

- 保持在 2-3 句话
- 使用面向用户的语言
- 突出最重要的变更
- 如有破坏性变更，必须在此提及

**Example**：

```markdown
## 版本概述

本次版本主要完成订单模块重构，优化下单性能，新增优惠券自动核销能力，修复若干稳定性问题。
```

### 变更概览 Section

变更概览部分以表格形式汇总各 Submodule 的变更统计：

- **Submodule**：子模块名称
- **提交数**：该 Submodule 的提交数量
- **变更文件数**：新增/修改/删除的文件数量
- **新增行数**：代码新增行数
- **删除行数**：代码删除行数

**Important**：

- 应包含所有已扫描的 Submodule，包括无变更的（标注"-"或"0"）
- 行数统计仅为参考，不代表实际工作量

**Example**：

```markdown
## 变更概览

| Submodule | 提交数 | 变更文件数 | 新增行数 | 删除行数 |
|-----------|--------|-----------|---------|---------|
| asdm-admin | 28 | 45 | +1,230 | -340 |
| asdm-agentorbit | 15 | 32 | +890 | -210 |
| asdm-cli | 3 | 5 | +120 | -30 |
| asdm-docs | — | — | — | — |
```

### 新功能 Section

新功能部分以表格形式展示，包含：

- **模块**：功能所属模块，使用"编号+名称"格式（如"1 认证与用户管理"）
- **Submodule**：变更所在的子模块
- **功能点**：功能名称
- **说明**：功能描述，面向用户视角
- **相关需求**：关联的需求/用户故事 ID

如需展示用户故事的完成条件（DoD），在新功能表格后补充 DoD 表格：

- **用户故事 ID**：用户故事标识
- **标题**：用户故事标题
- **DoD**：完成条件
- **状态**：完成状态

**Important**：

- 面向用户视角描述，而非技术实现细节
- 说明功能的应用场景和价值
- 模块列使用"编号+名称"格式，便于对照功能模块列表
- 如果关联了用户故事，以 DoD 表格形式展示

**Example**：

```markdown
## 新功能

| 模块 | Submodule | 功能点 | 说明 | 相关需求 |
|------|-----------|--------|------|----------|
| 3 项目管理 | asdm-admin | 批量创建项目 | 支持一次创建最多 50 个项目 | #12345 |
| 4 资源库管理 | asdm-admin | 自动归档 | 满足条件时自动归档过期资源 | #12360 |

**关联用户故事 DoD**：

| 用户故事 ID | 标题 | DoD | 状态 |
|------------|------|-----|------|
| US-1042 | 支持角色权限管理 | 功能实现、测试通过、文档已更新 | ✅ 已完成 |
```

### 功能优化 Section

功能优化部分以表格形式展示，包含：

- **模块**：优化所属模块，使用"编号+名称"格式
- **Submodule**：变更所在的子模块
- **优化点**：优化内容描述
- **效果**：优化带来的效果或收益

**Important**：

- 强调用户可感知的改进
- 尽量量化改进效果（如性能提升百分比）

**Example**：

```markdown
## 功能优化

| 模块 | Submodule | 优化点 | 效果 |
|------|-----------|--------|------|
| 1 认证与用户管理 | asdm-admin | 接口合并 | 首屏加载时间缩短 30% |
| 1 认证与用户管理 | asdm-agentorbit | 错误提示 | 提示更清晰，减少客服咨询 |
```

### Bug 修复 Section

Bug 修复部分以表格形式展示，包含：

- **模块**：缺陷所属模块，使用"编号+名称"格式
- **Issue ID**：缺陷标识
- **问题描述**：缺陷的简要描述
- **影响范围**：受影响的系统或端

**Important**：

- 描述问题对用户的影响，而非技术细节
- 如有已知限制，应在备注中说明

**Example**：

```markdown
## Bug 修复

| 模块 | Issue ID | 问题描述 | 影响范围 |
|------|----------|----------|----------|
| 3 项目管理 | #221 | 支付成功但订单状态未更新 | 所有支付方式 |
| 5 工作区管理 | #235 | iOS 端闪退 | v1.4.x 版本 |
```

### 数据变更 / 配置变更 Section

数据与配置变更部分以表格形式展示，包含：

- **Submodule**：变更所在的子模块
- **变更项**：新增/修改/删除的数据枚举、状态、字段或配置项
- **说明**：变更说明，含默认值和影响

**Important**：

- 有数据库变更、缓存刷新、开关配置的必须写清楚
- 迁移脚本路径应完整、可执行
- 配置变更应注明默认值和影响

**Example**：

```markdown
## 数据变更 / 配置变更

| Submodule | 变更项 | 说明 |
|-----------|--------|------|
| asdm-admin | 新增订单状态枚举 REFUNDED_PARTIAL | 部分退款状态，默认关闭 |
| asdm-admin | 新增配置项 coupon.auto_apply=true | 自动核销开关，默认开启 |

**数据库迁移脚本**：
- db/migration/V1.5.0__order_refund.sql
```

### 依赖变更 Section

依赖变更部分以表格形式展示，包含：

- **Submodule**：变更所在的子模块
- **依赖项**：依赖名称
- **变更前版本**：升级前的版本
- **变更后版本**：升级后的版本
- 如有安全修复，应在说明中重点标注

**Important**：

- 列出所有升级/降级/新增/移除的依赖
- 标注是否涉及安全修复

**Example**：

```markdown
## 依赖变更

| Submodule | 依赖项 | 变更前版本 | 变更后版本 |
|-----------|--------|-----------|-----------|
| asdm-admin | Spring Boot | 3.1.5 | 3.2.1 |
| asdm-admin | Fastjson | 1.2.83 | （移除，安全漏洞修复） |
| asdm-agentorbit | React | 18.2.0 | 18.3.1 |
```

### 上线影响与回滚策略 Section

上线影响与回滚策略部分应包含：

- **影响**：上线过程中和上线后对系统的影响
- **回滚方案**：出现问题时如何回滚

**Important**：

- 必须说明上线期间的影响（如停机时间）
- 回滚方案应具体可执行
- 如有数据库变更，应提供反向迁移脚本

**Example**：

```markdown
## 上线影响与回滚策略

**影响**：
- 订单中心停机约 10 分钟
- 老版本 App 仍可正常使用

**回滚方案**：
- 保留上一版本镜像
- 数据库支持反向迁移脚本
```

### 验证情况 Section

验证情况部分应包含：

- 冒烟测试结果
- 回归用例覆盖率
- UAT 验收结果

**Important**：

- 标注测试通过情况
- 如有未覆盖的场景，应注明

**Example**：

```markdown
## 验证情况

- 冒烟测试通过
- 回归用例覆盖率 95%
- UAT 验收通过（产品：张三）
```

### 备注 Section

备注部分用于记录其他需要说明的事项：

- 已知问题或限制
- 后续计划
- 需要特别关注的事项

## Usage Guidelines

生成 Release Note 时应遵循以下步骤：

1. **收集基本信息**：确认系统名称、版本号、发布类型、负责人等
2. **收集变更数据**：通过 Git 命令获取代码差异和提交记录
3. **分类变更内容**：根据提交消息和代码差异，将变更分类到对应章节
4. **关联缺陷和用户故事**：将变更与提供的缺陷清单和用户故事清单进行关联
5. **评估上线影响**：分析变更对系统的影响，制定回滚策略
6. **补充验证情况**：确认测试验证结果
7. **验证完整性**：确保所有变更条目都有描述，关联信息正确

**Important**：

- 无内容的章节应从文档中移除，不保留空章节
- 数据/配置变更、依赖变更必须在对应章节中明确列出
- 上线影响与回滚策略为必填章节
- 描述语言应面向最终用户，避免暴露内部实现细节

## Best Practices

编写 Release Note 时的最佳实践：

1. **面向用户编写**：使用用户能理解的语言，避免技术术语和内部实现细节
2. **突出价值**：说明变更对用户的价值和影响，而非仅仅罗列技术变更
3. **量化改进**：尽可能量化改进效果（如性能提升百分比、缺陷修复数量）
4. **及时关联**：确保缺陷修复和用户故事与提供的清单正确关联
5. **回滚方案完整**：上线影响与回滚策略应具体可执行
6. **数据变更透明**：数据库变更、配置变更、依赖变更必须明确列出

### Common Pitfalls to Avoid

- **过于技术化**：避免在描述中使用内部架构术语、类名、方法名等技术细节
- **遗漏上线影响**：上线影响与回滚策略为必填章节，不可省略
- **空章节**：如果某分类无内容，应删除该章节，不保留空标题
- **不一致的关联 ID**：确保引用的缺陷/用户故事 ID 与提供的清单一致
- **忽略数据变更**：有数据库变更、缓存刷新、开关配置的必须写清楚
- **缺失回滚方案**：每次发版必须有明确的回滚方案

## Checklist

生成 Release Note 前请检查：

- [ ] 基本信息完整（系统名称、版本号、发布类型、日期等）
- [ ] 版本概述简洁明了
- [ ] 变更概览表格包含所有已扫描的 Submodule
- [ ] 新功能表格完整（模块、Submodule、功能点、说明、相关需求）
- [ ] 模块列使用"编号+名称"格式
- [ ] 关联的用户故事 DoD 表格完整（ID、标题、DoD 条件、状态）
- [ ] Bug 修复表格完整（模块、Issue ID、问题描述、影响范围）
- [ ] 数据/配置变更表格完整（Submodule、变更项、说明）
- [ ] 依赖变更表格完整（Submodule、依赖项、变更前/后版本）
- [ ] 上线影响与回滚策略已提供
- [ ] 验证情况已记录
- [ ] 无空章节
- [ ] Markdown 格式已生成
- [ ] 语言一致且面向用户
