## Overview

本规范定义了数据库变更方案文档的结构和格式要求。此类文档用于对比需求数据模型与现有数据库结构，分析差异点，明确需要执行的变更操作，为生成可执行脚本提供依据。

**主要用途**:
- 完成数据建模后，设计具体变更
- PRD 评审时明确数据库变更范围
- 数据库变更实施前的方案评审
- 多方确认数据库变更计划

## Section Guidelines

### 1. 变更概述

变更方案的总体介绍。

**Guidelines**:
- 简要描述业务背景和变更目标
- 明确变更范围
- 提供变更统计

**Example**:
```
本变更方案针对"会员积分系统"功能的数据需求，
设计数据库变更操作。
变更范围包括新增 2 个表、修改 1 个现有表、新增 5 个字段。
预计影响 3 个现有表，估算涉及数据迁移量约 10 万条。
```

### 2. 差异分析

需求模型与现有结构的详细差异对比。

**Guidelines**:
- 按差异类型分类（新增表、修改表、删除表）
- 清晰列出每种差异的数量
- 标注高风险变更

**Example**:
```
### 2.1 新增表

| 序号 | 表名 | 说明 | 字段数 |
|------|------|------|--------|
| 1 | t_member_point | 会员积分账户表 | 8 |
| 2 | t_point_flow | 积分流水记录表 | 10 |
```

### 3. 变更操作清单

每个变更操作的详细 SQL 语句。

**Guidelines**:
- 按操作类型分组（新增表、修改表、索引变更、外键变更）
- 每个变更包含：说明、定义、SQL 语句
- SQL 语句应符合目标数据库语法

**Important**:
- CREATE TABLE 语句要完整，包含所有约束
- ALTER TABLE 语句要准确
- 注意字段顺序（MySQL）

**Example**:
```markdown
#### 3.1.1 t_member_point

**说明**: 会员积分账户表

**字段定义**:

| 字段名 | 数据类型 | 可空 | 默认值 | 主键 | 注释 |
|--------|----------|------|--------|------|------|
| id | BIGINT | NO | NULL | PK | 主键ID |
| member_id | BIGINT | NO | NULL | | 会员ID |
| point_balance | DECIMAL(12,2) | NO | 0 | | 积分余额 |
| created_at | DATETIME | NO | CURRENT_TIMESTAMP | | 创建时间 |

**SQL 语句**:
```sql
CREATE TABLE `t_member_point` (
    `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    `member_id` BIGINT NOT NULL COMMENT '会员ID',
    `point_balance` DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '积分余额',
    `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_member_id` (`member_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='会员积分账户表';
```
```

### 4. 数据迁移

如果变更涉及数据迁移，需要详细说明。

**Guidelines**:
- 说明迁移的源和目标
- 描述迁移逻辑
- 提供迁移 SQL

**Example**:
```
### 4.1 迁移需求列表

|------|----------|-----------|-------------|----------|
| 1 | 合并用户积分 | t_user.points | t_member_point.point_balance | 按 member_id 汇总 |
```

### 5. 执行计划

变更执行的顺序和时间安排。

**Guidelines**:
- 按依赖关系排序
- 明确每个阶段的内容
- 说明前提条件

**Important**:
- 新增操作在前，删除操作在后
- 数据迁移在 DDL 之后
- 外键约束最后添加

### 6. 影响评估

变更对系统的影响分析。

**Guidelines**:
- 评估影响范围（表数量、数据量、服务）
- 识别风险并制定缓解措施
- 明确停机窗口需求

**Example**:
```
| 风险类型 | 风险描述 | 影响等级 | 缓解措施 |
|----------|----------|----------|----------|
| 数据丢失 | 删除字段可能丢失数据 | 高 | 提前备份，确认无数据 |
| 服务中断 | 添加字段短暂影响 | 低 | 选择低峰期执行 |
```

### 7. 回滚方案

变更失败的回滚措施。

**Guidelines**:
- 明确回滚触发条件
- 提供详细的回滚步骤
- 准备回滚 SQL

### 8. 验收标准

验证变更成功的标准。

**Guidelines**:
- 定义可量化的验收标准
- 包含结构验证和数据验证
- 确保功能正常

## Usage Guidelines

生成数据库变更方案文档：

1. **Step 1**: 接收规划参数（Feature ID、数据库类型）
2. **Step 2**: 读取需求数据模型和现有数据库结构
3. **Step 3**: 分析两者差异
4. **Step 4**: 设计变更操作
5. **Step 5**: 评估变更影响
6. **Step 6**: 设计执行顺序
7. **Step 7**: 制定回滚方案
8. **Step 8**: 按本规范模板生成变更方案文档
9. **Step 9**: 保存文档到指定路径

**Important**:
- 确保覆盖所有数据变更需求
- 每个变更都应可回滚
- 减少对线上服务的影响
- 确保变更脚本可正确执行

## Best Practices

使用本规范时：

1. **完整性**: 覆盖所有数据变更需求，无遗漏
2. **可逆性**: 每个变更都应可回滚
3. **最小化影响**: 减少对线上服务的影响
4. **可执行性**: 确保变更脚本可正确执行

### Common Pitfalls to Avoid

- **变更遗漏**: 仔细对比需求模型和现有结构
- **依赖关系**: 注意表之间的依赖关系，正确排序
- **数据迁移**: 充分考虑数据迁移的需求和影响
- **回滚方案**: 每个高风险变更都要有回滚方案
