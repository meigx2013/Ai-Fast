# 数据需求模型规范

## Language Guidelines

本文档必须使用环境中检测到的响应语言。确保所有内容遵循：

1. **语言一致性**：整个文档使用同一种语言
2. **书写惯例**：遵循检测语言的书写风格和格式
3. **清晰性**：确保内容清晰易懂

**支持的语言**:
- 中文 (zh)
- 英文 (en)

---

## Overview

本规范定义了数据需求模型文档的结构和格式要求。此类文档用于从 PRD 文档中提取数据需求，构建需求数据模型，为后续数据库变更设计提供依据。

**主要用途**:
- 新功能开发时，将需求转化为数据实体定义
- PRD 评审时明确数据支撑需求
- 数据库变更设计的前置输入
- 团队统一数据实体定义

---

## Section Guidelines

### 1. 模型概述

数据模型的整体介绍，应清晰说明建模的目的和范围。

**Guidelines**:
- 简要描述业务场景
- 说明本次建模支持的功能
- 提供实体数、属性数、关系数统计

**Example**:
```
本次数据需求建模针对"会员积分系统"功能，
从 PRD 文档中提取了 5 个核心数据实体，
包括会员、积分账户、积分流水、积分规则、商品类别。
目标是支持会员积分的获取、查询、兑换等功能。
```

### 2. 数据实体清单

所有数据实体的概览表格。

**Guidelines**:
- 按业务重要性或功能模块排序
- 实体名使用业务术语
- 说明每个实体的主要作用

**Example**:
```
| 序号 | 实体名 | 实体说明 | 主要属性数 | 关联关系数 |
|------|--------|----------|------------|------------|
| 1 | 会员 | 系统注册用户 | 8 | 3 |
| 2 | 积分账户 | 会员积分余额 | 5 | 2 |
| 3 | 积分流水 | 积分变动记录 | 7 | 2 |
```

### 3. 实体详细定义

每个实体的完整属性定义，是数据模型的核心内容。

**Guidelines**:
- 按实体清单顺序逐个描述
- 属性名使用业务术语，字段名使用技术术语
- 数据类型应考虑目标数据库特性
- 合理设置主键（业务主键 vs 代理主键）

**Important**:
- 属性命名应使用业务术语，便于与业务方沟通
- 字段命名应遵循数据库命名规范
- 考虑未来可能的扩展需求

**Example**:
```markdown
### 3.1 会员

**实体说明**: 系统注册用户信息
**英文表名**: t_member
**表注释**: 会员信息表

#### 3.1.1 属性列表

| 序号 | 属性名 | 字段名 | 数据类型 | 长度 | 可空 | 默认值 | 主键 | 说明 |
|------|--------|--------|----------|------|------|--------|------|------|
| 1 | 会员ID | member_id | BIGINT | - | NO | NULL | PK | 会员唯一标识 |
| 2 | 会员名称 | member_name | VARCHAR | 50 | NO | NULL | | 会员昵称 |
| 3 | 手机号 | phone | VARCHAR | 20 | NO | NULL | | 注册手机号 |
| 4 | 会员等级 | level | TINYINT | - | NO | 1 | | 等级：1-普通，2-银卡，3-金卡 |
```

### 4. 实体关系图

实体之间的关系描述。

**Guidelines**:
- 清晰标注关系类型（1:1、1:N、M:N）
- 使用文本方式绘制 E-R 图
- 说明外键字段的来源

**Example**:
```
### 4.1 关系清单

| 序号 | 关系名 | 类型 | 源实体 | 源字段 | 目标实体 | 目标字段 | 说明 |
|------|--------|------|--------|--------|----------|----------|------|
| 1 | 会员-账户 | 1:1 | 会员 | member_id | 积分账户 | member_id | 每个会员一个积分账户 |
| 2 | 会员-流水 | 1:N | 会员 | member_id | 积分流水 | member_id | 会员有多条积分流水 |
| 3 | 规则-商品 | M:N | 积分规则 | rule_id | 商品类别 | category_id | 中间表：t_rule_category |

### 4.2 E-R 图

┌─────────────┐       ┌─────────────┐       ┌─────────────┐
│   会员      │──1:1──│ 积分账户    │       │  积分规则   │
│  t_member   │       │t_point_acc  │       │ t_point_rul │
└─────────────┘       └─────────────┘       └─────────────┘
       │                                         │
       │ 1:N                                      │ M:N
       ▼                                         ▼
┌─────────────┐                           ┌─────────────┐
│  积分流水   │                           │规则商品关联 │
│t_point_flow │                           │t_rule_categ │
└─────────────┘                           └─────────────┘
```

### 5. 数据字典

统一的字段类型和枚举定义。

**Guidelines**:
- 定义通用字段（创建时间、更新时间等）
- 定义业务枚举值
- 确保全模型一致

**Example**:
```

|--------|----------|------|----------|

| updated_at | DATETIME | 更新时间 | 所有表 |
| deleted | TINYINT | 删除标记 | 需软删除的表 |

### 5.2 枚举定义

| 枚举名 | 值 | 说明 |
|--------|-----|------|
| MemberLevel | 1=普通会员 | 普通会员等级 |
| | 2=银卡会员 | 银卡会员等级 |
| | 3=金卡会员 | 金卡会员等级 |
```

## Usage Guidelines

生成数据需求模型文档：

1. **Step 1**: 接收建模参数（Feature ID、PRD 文档路径）
2. **Step 2**: 读取 Feature PRD 文档
3. **Step 3**: 从 PRD 中识别数据实体
4. **Step 4**: 定义实体属性
5. **Step 5**: 定义实体关系
6. **Step 6**: 按本规范模板生成数据模型文档
7. **Step 7**: 保存文档到指定路径

**Important**:
- 以业务需求为出发点，不是技术实现
- 确保覆盖所有业务场景所需数据
- 使用业务术语命名，便于沟通

## Best Practices

使用本规范时：

1. **业务导向**: 以业务需求为出发点，不是技术实现
2. **实体完整性**: 确保覆盖所有业务场景所需数据
3. **关系清晰**: 明确实体间的关系和业务含义
4. **命名规范**: 使用业务术语命名，便于沟通

### Common Pitfalls to Avoid

- **实体遗漏**: 仔细阅读 PRD，识别所有隐含的数据实体
- **属性不全**: 考虑每个实体的完整属性，包括状态、时间等
- **关系错误**: 正确识别实体间的关系类型
- **类型选择**: 选择合适的数据类型，考虑扩展性
