## Overview

本规范定义了数据库结构分析报告的结构和格式要求。此类文档用于记录和分析现有数据库的结构，作为后续数据库变更设计的基础参考。

**主要用途**:
- 了解现有数据库结构作为变更设计的基准
- 为数据库变更方案提供现有结构信息
- 支持数据库重构前的结构调研
- PRD 文档评审时了解现有数据支撑能力

## Section Guidelines

### 1. 概述

数据库整体情况的摘要，应简洁明了。

**Guidelines**:
- 提供表、字段、索引、外键的数量统计
- 说明数据库类型和版本信息
- 描述数据源（DDL文件或连接信息）

**Example**:
```
本分析报告涵盖XXX系统的数据库结构，共包含15个业务表，
约120个字段，25个索引，8个外键关系。数据库类型为MySQL 8.0，
数据来源于最新的DDL文件。
```

### 2. 表清单

所有表的概览表格，便于快速了解数据库全貌。

**Guidelines**:
- 按表名排序或按业务模块分组
- 每行包含表名、表注释、字段数、索引数、外键数
- 表名应与数据库中一致

**Example**:
```
| 序号 | 表名 | 表注释 | 字段数 | 索引数 | 外键数 |
|------|------|--------|--------|--------|--------|
| 1 | t_user | 用户信息表 | 12 | 3 | 1 |
| 2 | t_order | 订单信息表 | 18 | 5 | 2 |
```

### 3. 详细表结构

每个表的完整定义，是分析报告的核心内容。

**Guidelines**:
- 按表清单顺序逐个描述
- 字段定义包含：字段名、数据类型、可空、默认值、主键、注释
- 索引定义包含：索引名、类型、字段、唯一性
- 外键定义包含：外键名、源字段、目标表、目标字段

**Important**:
- 数据类型应与数据库定义完全一致
- 注意 MySQL 的 AUTO_INCREMENT、PostgreSQL 的 SERIAL 等特性
- 保留原始的字段注释

**Example**:
```markdown
### 3.1 t_user

**表注释**: 用户信息表

**字段定义**:

| 字段名 | 数据类型 | 可空 | 默认值 | 主键 | 注释 |
|--------|----------|------|--------|------|------|
| user_id | BIGINT | NO | NULL | PK | 用户ID |
| user_name | VARCHAR(50) | NO | NULL | | 用户名 |
| email | VARCHAR(100) | YES | NULL | | 邮箱 |
| status | TINYINT | NO | 1 | | 状态：0-禁用，1-正常 |
| created_at | DATETIME | NO | CURRENT_TIMESTAMP | | 创建时间 |
```

### 4. 索引清单

所有索引的汇总表。

**Guidelines**:
- 按索引名排序或按表分组
- 说明索引类型（BTREE、HASH等）
- 标注是否唯一索引

**Example**:
```
| 索引名 | 表名 | 类型 | 字段 | 唯一 |
|--------|------|------|------|------|
| idx_user_name | t_user | BTREE | user_name | NO |
| idx_email | t_user | BTREE | email | YES |
| uk_user_email | t_user | BTREE | email | YES |
```

### 5. 外键关系图

表与表之间的关联关系。

**Guidelines**:
- 提供关系列表，包含完整的外键信息
- 使用文本方式绘制简单的 E-R 图
- 说明级联操作（ON DELETE、ON UPDATE）

**Example**:
```
┌─────────────┐       ┌─────────────┐       ┌─────────────┐
│   t_user    │──1:N──│   t_order   │──N:1──│ t_product   │
│   用户表    │       │   订单表    │       │   商品表    │
└─────────────┘       └─────────────┘       └─────────────┘
```

## Usage Guidelines

生成数据库结构分析报告：

1. **Step 1**: 接收分析参数（数据源类型、路径、数据库类型）
2. **Step 2**: 读取数据库上下文（DDL文件或连接数据库）
3. **Step 3**: 提取数据库元素（表、字段、索引、外键）
4. **Step 4**: 按本规范模板生成分析报告
5. **Step 5**: 保存报告到指定路径

**Important**:
- 确保提取所有表、字段、索引、外键
- 数据类型的解析要准确反映原始定义
- 使用清晰的结构化格式输出
- 保留原始 DDL 以便追溯

## Best Practices

使用本规范时：

1. **完整性检查**: 确保提取了所有数据库元素，包括隐藏列、系统字段
2. **准确性**: 数据类型、默认值等必须与原始定义完全一致
3. **可读性**: 使用清晰的层次结构，适当使用标题和表格
4. **可追溯性**: 在附录中保留原始 DDL 语句

### Common Pitfalls to Avoid

- **遗漏字段**: 特别检查是否遗漏了系统字段（如创建时间、更新时间）
- **类型错误**: 解析数据类型时要准确，如 VARCHAR 的长度、DECIMAL 的精度
- **索引遗漏**: 索引信息可能分散在 CREATE TABLE 和独立 CREATE INDEX 语句中
- **外键遗漏**: 外键可能通过 ALTER TABLE 添加，需全面检查
